# PR

PR（`PullRequest`）は、Issue に応えて、作った時点の成果物（`base`）に対する実装の変更と、範囲を持つ。CI の結果と本文、本文の要約（タイトル）も持つ。

## 範囲

範囲（`PullRequest.Scope`）は、Issue のとおりか、変えたかのどちらか。変えたなら、変えた変更要件と、変えた理由を持つ。範囲を変えたのに理由を書かない PR は作れない。

## 本文

本文（`PullRequest.Body`）は、範囲・検証・見積もり・実装の理由を持つ。本文は Issue・作った時点の成果物・変更後の実装・CI 結果に依存する型なので、その変更の検証しか持てない（[検証](../Verification/verification.md)）。見積もりは既定路線の費用で、既定路線の実装はないので提案者が見積もる。

## 届けることと解決すること

- 届ける（`PullRequest.Delivers`）：変更後の成果物が正しく、ルールに適合する。
- 解決する（`PullRequest.Resolves`）：Issue の変更要件どおりに実現し、正しく、ルールに適合する。

範囲を変えていなければ、この二つは一致する（`PullRequest.delivers_iff_resolves`）。

## 承認

承認（`PullRequest.Approval`）は、人間が PR を受け入れる判断で、受け入れるかどうかの二値である。正しさ、理由と見積もりの妥当さ、要求の価値はここで判断する。範囲を変えた PR の承認は、その範囲の変更を認めることでもある。承認された PR だけがリポジトリの履歴に入る（[リポジトリ](../Repository/repository.md)）。

## 文書

PR は、レビュアーが読む文書として書く。その文書の種類（`PullRequest.genre`）は、[文書の種類](../../Documentation/Document/Genre/genre.md)の考え方を PR に当てはめたもので、レビュアーに承認するかを判断してもらう。判断は承認するかしないかの二値なので、承認したら何を受け入れたことになるかを、範囲・変更・検証で過不足なく書く。

| 役割 | 働き | ふさわしい文体 |
| --- | --- | --- |
| 要約（`PullRequest.Role.summary`） | この PR が何をするかを示す（タイトル） | 言い切る、新しい語を導入しない |
| 判断してほしいこと（`PullRequest.Role.decision`） | 承認するか（逸脱の理由を受け入れるかも含む）について、何に答えればよいかを示す | 依頼する、はい／いいえで答えられる、新しい語を導入しない |
| 範囲（`PullRequest.Role.scope`） | 承認したら何を受け入れるかの境界を示す（応える Issue と、Issue から変えた点） | 具体的 |
| 変更（`PullRequest.Role.change`） | 実装の変更の要点を示す | 具体的 |
| 検証（`PullRequest.Role.verification`） | 正しいと信じてよい根拠を示す（CI の結果は書き写さない） | 具体的、つながりを示す |
| 逸脱の理由（`PullRequest.Role.deviation`） | 既定路線から外れてよい理由を示す（逸脱があるときだけ） | つながりを示す |

節はこの順に並べる（`PullRequest.order`）。判断してほしいことを要約の直後に置くのは、レビュアーが何を判断するために読むのかを先に知らせるためである。逸脱の理由は逸脱があるときだけ、最後に置く。節をまたいでは、Issue と同じ語を使い、言い直さない。

### 話題と、内容を節にする方針

PR の内容の話題は、承認する人が答えを知りたい問いで、PR のフィールドから立てる。PR の種類は、どの話題をどの役割の節に置くかの方針（`PullRequest.place`）を持つ。

| 話題 | 出どころ | 置く節 |
| --- | --- | --- |
| 要約 | `title` | 要約 |
| 承認するか | PR そのもの | 判断してほしいこと |
| 何を変えるのか | `scope` の変更要件 | 範囲 |
| 実装をどう変えたか | `base` から `implementations` への差 | 変更 |
| 費用の見積もり | `estimate` | 変更 |
| 確かめたこと | `verification` の確かめた部分 | 検証 |
| 外れてよい理由 | 範囲を変えた理由、確かめない理由、見積もりを超えたときの実装の理由 | 逸脱の理由 |

見積もりは、実装の理由が要るかどうかの基準である。基準を大きく書けば理由を書かずに済むので、承認する人が水増しを確かめられるよう、超えたかどうかにかかわらずいつも伝える。実装の費用の基準なので、変更の節に置く。

### 内容が PR を表す

文書の種類に従うだけでは、文書が PR の中身を伝えているとは限らない。そこで、内容が PR を表すこと（`PullRequest.Describes`）を、次の条件で定める。

- 伝えるべき部分（`PullRequest.parts`）のそれぞれについて、それを述べる事柄（`PullRequest.States`）が内容にあり、その話題は部分の話題である。伝えるべき部分は、タイトル・承認を求めること・範囲の変更要件・実装の変更・見積もり・検証の確かめた部分・逸脱の理由一つずつである。逸脱の理由には、承認で読まなければならないもの（[費用](../Cost/cost.md)の逸脱）をすべて含める。
- 内容には、どの部分も述べない事柄がない。

内容を節にするのは文書の仕事で、意味を保つことと種類に従うことで確かめる。逸脱がある PR を表す内容を、意味を保ち種類に従って節にした文書には、逸脱の理由の節がある（`PullRequest.Describes.deviation_mem`）。種類の並びでは省いてよい節が、PR を表すことで必須になる。
